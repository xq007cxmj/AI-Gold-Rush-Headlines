# 我是怎么用 Claude Code 这个 Agent，把一个项目从 0 落地的

> 本文是我在开发一个类「今日头条」的资讯网站（Vue 3 + FastAPI）时，用 Claude Code 等 Agent 完成项目落地的实践经验总结。重点不是「AI 帮我写了代码」，而是**我如何设计 Agent 的工作流，让它在受控、可验证的前提下稳定交付**。

## 一、先澄清一个误区

很多人提到「用 AI 写代码」，想到的是「给一句话，让它吐一坨代码」。这种一次性生成的模式，规模一大就不稳定：代码风格跑偏、上下文记不住、错了也不知道从哪改。

我用的方式是把 Agent 当成一个**有规划、能调用工具、会自己验证**的开发智能体，配合一套明确的工作流，让它真正「落地」而不是「生成」。

## 二、核心：Agentic Loop（规划—执行—观察—再规划）

一个可靠 Agent 的底层是循环，而不是一次对话：

```
用户需求 → 拆解任务 → 规划 → 调用工具 → 观察结果 → 验证 → 不通过则再规划 → 通过则提交
```

- **规划（Plan）**：把目标拆成可执行的小步骤。
- **执行（Act）**：调用工具（读文件、写代码、搜索、重构、运行调试）。
- **观察（Observe）**：读取工具返回，判断是否达到预期。
- **再规划（Re-plan）**：没达到就调整方案继续。

这个项目里，我把一个资讯网站拆成四个模块——**新闻、用户、收藏、历史**，每个模块都是一个可独立推进的子任务，先明确「输入 / 产出 / 验收标准」，再交给 Agent。这样并行推进、互不干扰，也不会因为一次干太多而失控。

## 三、需求拆解：把「模糊」翻译成「可验收」

Agent 最怕模糊需求。我会把每件事写成：

```
目标：实现新闻分页列表接口
输入：categoryId、page、pageSize
产出：{ list, total, has_more } 格式的 JSON
约束：遵循 routers→crud→models→schemas 分层；写中文注释；统一 code/message/data 响应
验收：分页正确、超过总量时 has_more=false
```

「一段话 + 验收点」比「帮我写个新闻接口」好太多。因为 Agent 有明确的判断依据，我知道它交付得对不对。

## 四、上下文管理：大项目怎么不「失忆」

Agent 的上下文是有限的。项目一大，最怕它做着做着忘了前面的约定。

我的做法：

- **模块化推进**：一次只处理一个模块，完成后进入下一个。
- **阶段性总结**：每完成一个模块，用一段话总结当前进度和已定约定，作为下一轮的上下文起点。
- **局部注入**：改某个文件时，只把相关代码 + 上下文喂给它，而不是把整个项目都塞进去。

这样上下文始终「轻」且「连贯」，Agent 不会因为信息过载而前后不一致。

## 五、人在回路（Human-in-the-loop）

Agent 高产出，但也需要约束。我的分工是：

- **我定方向和架构**：分层、目录、接口规范、数据库设计。
- **Agent 执行**：按既定规范写代码、做缓存优化、产出文档。
- **我审查**：关键改动逐行看，跑通验证再合并。

不是「AI 全自动」，而是**人做决策、AI 干活、人来把关**。这个边界想清楚，才有可控的质量。

## 六、踩过的坑与对策

| 坑 | 对策 |
| --- | --- |
| 一次性生成太多，越到后面越乱 | 拆成模块，明确验收点，逐步推进 |
| 上下文记不住前面的约定 | 阶段性总结 + 局部注入 |
| 直接生成、没有验证就跑 | 建立「自检 → 审查 → 运行验证」闭环 |
| 无序改动、难以回滚 | 最小权限 + 先出方案再落地 |

## 七、收获

用 Agent 落地项目，最大的收获不是「快」，而是**沉淀了一套可复用的工作流**：如何拆解、如何写指令、如何管理上下文、如何验证。这套方法可以迁移到下一个项目，迭代成本大幅下降。
