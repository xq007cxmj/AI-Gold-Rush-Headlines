# Agent 工具调用与 Skill 沉淀：让智能体稳定交付，而不是随机生成

> 上一篇讲了 Agent 工作流。这篇聚焦一个关键问题：**为什么同样一句话，Agent 有时很稳、有时像换了个脑子？** 答案往往在「工具调用」和「Skill 化」上。

## 一、工具调用：Agent 的「手脚」

Agent 不能只靠「想」，它需要**调用工具**去改变世界。对一个开发 Agent 来说，工具就是：读文件、写文件、搜索、重构、运行调试、执行命令……

我理解的工具调用是三层：

1. **能力层**：Agent 能用哪些工具（文件读写、检索、执行等）。
2. **约束层**：哪些工具允许用、哪些要审批、有没有最小权限。
3. **编排层**：怎么把多个工具组合成一个有顺序、能复用、可验证的执行链。

这个项目里，Agent 通过工具完成的是「**文件读写 + 搜索 + 重构 + 调试**」这套组合，而不是一次聊天吐一坨代码。它读现有代码 → 搜索模式 → 写新模块 → 运行验证 → 发现问题 → 改回来。这才是「落地」和「生成」的区别。

## 二、Skill：把「经验」从脑子里搬到仓库里

每次都要跟 Agent 重新描述项目规范是很累的，而且每次描述都可能不一致。**Skill 就是把常在嘴边的那套约束固化成仓库里的文件**，Agent 在需要时加载，而不是每次从零理解。

Skill 化的关键是把四样东西分开放：

| 分类 | 举例 |
| --- | --- |
| 主指令 | 角色定位、总体目标、执行边界 |
| 参考文档 | 接口约定、目录规范、错误处理规则 |
| 软件配方 | 数据库模型、缓存规范、可复用模板 |
| 测试代码 | 校验用例、验证脚本 |

这样设计的好处：

- **复用**：下一模块直接加载同一套 Skill，风格一致，不用重新写一遍需求。
- **可审计**：Agent 每个决定都有对应依据，出问题能回溯到规范本身。
- **可测试**：把校验逻辑独立出来，先让用例过关，再让 Agent 执行。

## 三、为什么要「固化」而不是「每次说」

想象两种做法：

**做法 A**：每次说「记得用分层架构、中文注释、统一响应」。—— 会被稀释，越到后面越走样。

**做法 B**：把规范写成 Skill 文档，Agent 需要时读它。 —— 每次都是同一份权威依据，不改就不漂移。

显然 B 更稳。这也是「**把 Agent 当助手、靠 prompt 临场发挥**」和「**把 Agent 当交付系统、靠沉淀的规范约束**」的分水岭。

## 四、落地效果

在这个项目里，通过 Skill 沉淀 + 工具调用编排，我实现了几件事：

- 四个业务模块（新闻 / 用户 / 收藏 / 历史）按同一套规范开发，风格统一。
- 关键优化（Redis 缓存、索引、统一响应与异常封装）以明确指令传达给 Agent，再审查落地。
- 出问题（异步会话、唯一约束、分页边界）时，把上下文喂给 Agent → 定位 → 修复 → 复查，形成稳定闭环。

## 五、给你的建议

1. **先定边界，再让 Agent 干活**：架构、目录、规范先定死。
2. **规范做成 Skill，而不是口头话**：沉淀成文件，可复用、可审计、可测试。
3. **让 Agent 调工具链干活，别只让它说话**：读、写、检索、执行、验证，组合起来才有生产力。
4. **建立验证闭环**：不验证就提交，等于把风险全压给「它应该没错」。
